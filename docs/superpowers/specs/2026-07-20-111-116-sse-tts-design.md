## #111 — estado terminal del stream SSE

### Causa raíz

La tarea productora `_run()` captura `RuntimeError`, sólo lo registra y siempre inserta el sentinel `None`. El generador consumidor no conoce el fallo y ejecuta incondicionalmente el epílogo de éxito: chunk con `finish_reason="stop"` y `data: [DONE]`. Además, `tracker.close()` usa su estado por defecto de éxito.

### Diseño

`generate()` mantendrá una referencia `orchestrator_error` compartida con `_run()`:

1. `_on_token()` seguirá encolando chunks de contenido sin cambios.
2. `_run()` guardará cualquier `RuntimeError` producido por `call_orchestrator()`.
3. En `finally`, `_run()` insertará primero el sentinel `None`, preservando la garantía actual frente a fallos de `tracker.close()`.
4. El tracker se cerrará con `status="error"` cuando exista `orchestrator_error`; en éxito conservará el estado por defecto.
5. Tras drenar la cola, el consumidor elegirá un único epílogo:
   - **éxito:** `finish_reason="stop"` y `data: [DONE]`;
   - **error:** primero un frame top-level `error` cuyo `message` sea `str(orchestrator_error)` y cuyo `type` sea `"server_error"`, después un chunk con `finish_reason="error"`, y nunca `[DONE]`.

La cola conserva orden FIFO, por lo que cualquier token producido antes del error se entrega antes de los frames terminales. El status HTTP sigue siendo 200 porque un `StreamingResponse` no puede cambiarlo después de iniciar el stream; el error se expresa en el protocolo SSE.

### Pruebas TDD

- error antes del primer token;
- token parcial seguido de error.

Ambos comprobarán el objeto SSE `error`, el chunk `finish_reason="error"`, la ausencia de `[DONE]` y de `finish_reason="stop"`, y el estado `"error"` de la sesión/tracker. El caso post-token comprobará además que el contenido parcial previo sigue presente.

## #116 — autenticación y cleanup de `TTSClient`

### Causa raíz

`connect()` sólo cierra el socket cuando `auth_err` fue asignado dentro de `except Exception`. En Python actual, `asyncio.CancelledError` hereda de `BaseException`, no entra en ese `except` y deja `auth_err` vacío. Si la cancelación ocurre después de asignar `self.ws` y antes de validar `auth_ok`, el `finally` no cierra el socket.

### Diseño

`connect()` usará `_authenticated = False` como fuente de verdad del cleanup:

1. Abrirá el WebSocket y enviará el frame `auth` actual.
2. Esperará la respuesta con `asyncio.wait_for(self.ws.recv(), timeout=settings.TTS_AUTH_TIMEOUT_S)`.
3. Sólo marcará `_authenticated = True` después de validar un frame `auth_ok`.
4. Capturará `asyncio.CancelledError` explícitamente y la relanzará sin envolverla ni convertirla en un fallo ordinario.
5. En `finally`, si el socket existe y no está autenticado, intentará cerrarlo con código 1000, tolerará errores secundarios del cierre y asignará `self.ws = None`.

El cleanup cubrirá cancelación durante el envío o recepción de auth, timeout, cierre remoto, JSON inválido y rechazo de credenciales. Si `websockets.connect()` se cancela antes de devolver un objeto, `self.ws` todavía será `None` y la propia librería será responsable de limpiar la conexión parcial.

Se añadirá `TTS_AUTH_TIMEOUT_S: float = 10.0` a `Settings` y se documentará en la lista de variables de entorno de `CLAUDE.md`. La convención de direcciones `host:port` no cambia.

### Pruebas TDD

Se ampliará `tests/unit/test_tts_client_connect_leak.py` con:

- un `recv()` colgado, cancelación explícita del task y comprobación de que `CancelledError` se propaga, `close()` se invoca y `client.ws is None`;
- un timeout reducido mediante monkeypatch y comprobación del mismo cleanup;
- una aserción `client.ws is None` en el caso ya existente de auth fallida.
