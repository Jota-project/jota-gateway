## Bugs Críticos 🔴

### Bug 1 — `bridge.py:248` — Segundo `{type:'send'}` filtra el task anterior

**Estado:** ✅ Resuelto

**Archivo:** `src/services/bridge.py`, línea 248

**Descripción:**
Cuando llega un segundo mensaje `{"type":"send"}` mientras el primer turn del orquestador aún
corre, `self._active_turn` se sobreescribe con el nuevo task **sin cancelar el anterior**.
El task viejo queda huérfano (no referenciado por `_active_turn`) y sigue corriendo, creando
dos turns concurrentes: dos `TTSClient` enviando tokens y audio entrelazados al mismo WebSocket.

**Código problemático:**
```python
# line 248
self._active_turn = asyncio.create_task(self._call_orchestrator(text))
```

**Scenario de fallo:**
1. Cliente envía `{"type":"send","text":"hola"}` → Task A creado, `_active_turn = A`
2. Antes de que A termine, cliente envía `{"type":"send","text":"mundo"}` → `_active_turn = B`
3. Task A sigue corriendo (sin referencia). Task A + Task B envían tokens y audio concurrentes.
4. `_cancel_active_turn()` solo puede cancelar B. A corre hasta completar.

**Fix:** Llamar `await self._cancel_active_turn()` antes de crear el nuevo task (idéntico a lo
que ya hace el barge-in).

```python
# Fix
await self._cancel_active_turn()
self._active_turn = asyncio.create_task(self._call_orchestrator(text))
```

### Bug 2 — `bridge.py:252` — Modo texto plano bloquea el input loop

**Estado:** ✅ Resuelto

**Archivo:** `src/services/bridge.py`, línea 252

**Descripción:**

```python
# line 252

```

**Fix:**
```python
await self._cancel_active_turn()
self._active_turn = asyncio.create_task(self._call_orchestrator(text_data))
```

### Bug 3 — `openclaw_client.py:207` — `stream_response()` sin guard de concurrencia

**Estado:** ✅ Resuelto

**Archivo:** `src/services/orchestrators/openclaw_client.py`, líneas 207-209

**Descripción:**
`stream_response()` escribe `_active_req_id` y `_turn_queue` sin ningún lock ni comprobación.
Dos llamadas concurrentes (e.g. sesión WebSocket + endpoint HA REST) corrompen mutuamente
el estado: el segundo caller sobreescribe la queue, el listener `_listen` deja de rutear
frames al primer caller, que queda colgado en `_turn_queue.get()` sin timeout.

**Código problemático:**
```python
req_id = str(uuid.uuid4())
self._active_req_id = req_id     # line 208 — sin lock
self._turn_queue = asyncio.Queue()  # line 209 — sin lock
```

**Fix:** Añadir `asyncio.Lock` que envuelva todo el turn, o un assert que falle rápido:
```python
if self._active_req_id:
    raise RuntimeError("OpenClawClient: concurrent stream_response — only one turn at a time")
```

## Bugs Altos 🟠

### Bug 4 — `openai_routes.py:59` — Streaming SSE es falso (buffering completo)

**Estado:** ✅ Resuelto

**Archivo:** `src/api/openai_routes.py`, líneas 59-76

**Descripción:**
El generador `generate()` acumula todos los chunks en `chunks: list[str]` dentro de
`_on_token` (append, no yield). El for-loop que hace `yield` está **después** del
`await call_orchestrator(...)`. El cliente HA no recibe ningún dato hasta que la
generación completa. Funciona idéntico al path no-streaming pero con framing SSE.

**Código problemático:**
```python
chunks = []
async def _on_token(t: str):
    chunks.append(f"data: {json.dumps(chunk)}\n\n")  # acumula

await call_orchestrator(...)  # espera todo
for chunk in chunks:
    yield chunk  # solo ahora envía
```

**Fix:** Hacer yield directamente desde `_on_token` usando una `asyncio.Queue` o
convirtiendo `_on_token` en un generador cooperativo. La forma más simple:
```python
async def _on_token(t: str):
    chunk = {...}
    yield f"data: {json.dumps(chunk)}\n\n"  # no es posible directo — usar Queue
```
Implementación recomendada: `asyncio.Queue` + consumidor que hace yield, o refactorizar
para que `call_orchestrator` sea un async generator.

### Bug 5 — `bridge.py:371` — `tts.end()` se saltea en `ConnectionClosed`

**Estado:** ✅ Resuelto

**Archivo:** `src/services/bridge.py`, línea 371

**Descripción:**
`pipe_tokens()` solo captura `RuntimeError`. Si `call_orchestrator` lanza cualquier otra
excepción (e.g. `websockets.ConnectionClosed`, `asyncio.CancelledError`), la excepción
sale de `pipe_tokens()` saltando `tts.end()` en line 372. `pipe_audio()` queda bloqueado
esperando un frame `done` que nunca llega. `tts.close()` en el `finally` de gather
cierra el WS sin enviar `end` primero.

**Fix:**
```python
async def pipe_tokens():
    try:
        await call_orchestrator(...)
    except RuntimeError as e:
        try:
            await self.client_ws.send_json({"type": "error", "content": str(e)})
        except Exception:
            pass
    finally:          # ← cambiar except por finally para tts.end()
        if tts:
            await tts.end()
```

### Bug 6 — `reconnecting.py:86` — `ConnectionClosed` se propaga sin envolver

**Estado:** ✅ Resuelto

**Archivo:** `src/services/orchestrators/reconnecting.py`, línea 86

**Descripción:**
`stream_response()` delega con `async for event in self._client.stream_response(...)` sin
try/except. Un `ConnectionClosed` o cualquier excepción no-OrchestratorEvent del WS
interno sube sin convertir a `OrchestratorEvent(type="error")`, pasa por
`call_orchestrator` (también sin try/except en el loop), y llega a `pipe_tokens()` que
solo captura `RuntimeError`. La excepción cruda cancela el `asyncio.gather`, el cliente
no recibe `{type:"done"}`.

**Fix:** Envolver la delegación:
```python
try:
    async for event in self._client.stream_response(...):
        yield event
except asyncio.CancelledError:
    raise
except Exception as e:
    yield OrchestratorEvent(type="error", content=str(e))
```

### Bug 7 — `openai_routes.py:95` — HTTP 200 en error del orquestador

**Estado:** ✅ Resuelto

**Archivo:** `src/api/openai_routes.py`, línea 95

**Descripción:**
El path no-streaming captura `RuntimeError` del orquestador y lo loguea, pero continúa y
retorna `JSONResponse` con HTTP 200 y `content=""`. Home Assistant recibe una respuesta
exitosa con mensaje vacío, sin indicación del fallo.

**Fix:** Retornar HTTP 502/503 en el `except`:
```python
except RuntimeError as e:
    logger.error(f"HTTP orchestrator error: {e}")
    await tracker.close()
    return JSONResponse({"error": str(e)}, status_code=502)
```

## Bugs Medios 🟡

### Bug 8 — `bridge.py:70` — Tasks cancelados sin `await`

**Estado:** ⬜ No aplica (investigado, sin impacto práctico)

**Archivo:** `src/services/bridge.py`, línea 70

**Descripción:**
`close_all()` llama `task.cancel()` en los background tasks pero no los awaita. En principio
esto podría generar `Task exception was never retrieved` y cleanup ejecutado contra recursos ya
cerrados.

**Investigación:**
El fix naive (`asyncio.gather(*cancels, return_exceptions=True)`) bloquea el event loop mientras
espera la cancelación de `listen_loop` (que hace I/O en el WS del transcriber). El Starlette
TestClient en el hilo del test queda esperando el cierre del WebSocket, agota su timeout y lanza
`concurrent.futures.CancelledError` — regresión en los tests de integración.

Además, el riesgo declarado no existe en este codebase:
- `listen_loop` y `watchdog` al ser cancelados salen con `CancelledError` (no `Exception`).
  Python no genera "Task exception was never retrieved" para `CancelledError`.
- `listen_loop` no accede a ningún recurso después de recibir `CancelledError`: simplemente
  propaga la excepción fuera del `async for`.

**Conclusión:** Patrón mejorable en general, pero sin consecuencias reales aquí. Cualquier fix
debe ser no-bloqueante (e.g. callbacks, timeout muy corto) para no interferir con el cierre WS.

### Bug 10 — `reconnecting.py:127` — Sin circuit-breaker real en estado DEGRADED

**Estado:** ✅ Resuelto

**Archivo:** `src/services/orchestrators/reconnecting.py`, línea 127

**Descripción:**
Después de agotar `ORCHESTRATOR_RECONNECT_MAX_DURATION` y entrar en DEGRADED, cada llamada
a `ping()` o `stream_response()` reinicia `_reconnect_loop()` vía `_ensure_reconnecting()`,
dando otra ventana completa de reintentos. Bajo una caída prolongada el sistema oscila
indefinidamente entre DEGRADED y RECONNECTING en cada request.

**Fix:** Añadir un flag `_reconnect_exhausted: bool = False` que solo se resetea en un
`connect()` exitoso o en `trigger_reconnect()` explícito:
```python
def _ensure_reconnecting(self) -> None:
    if self._reconnect_exhausted:
        return  # circuit open — solo trigger_reconnect() puede resetear
    if not self._reconnect_task or self._reconnect_task.done():
        self._state = OrchestratorState.RECONNECTING
        self._reconnect_task = asyncio.create_task(self._reconnect_loop())
```
